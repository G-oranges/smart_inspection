# 数据导入向导 (Import Wizard) 完整实施方案

本方案参考 Navicat 的导入向导交互, 统一 6 步导入流程, 仅支持 xls/xlsx。

## 1. 范围与目标

### 1.1 目标

- 统一所有“导入”为同一套导入向导 (Import Wizard) 交互范式, 在不同业务页面复用同一流程与组件。
- 向导内完成: 模板下载 -> 文件上传与 Sheet 选择 -> 字段映射 -> 数据预检 -> 冲突策略 -> 执行与结果复盘。
- 数据口径拆分清晰: 学生导入只负责学生基础信息与组织学籍属性; 宿舍导入只负责宿舍静态属性; 入住导入只负责学生与床位/宿舍的分配关系。

### 1.2 不做的事项 (边界)

- 不在导入页面内做逐格编辑修复或在线批量编辑。
- 冲突与错误行通过筛选 + 下载问题行文件, 由用户在 Excel 中修复后增量重导。
- 不扩展除已确认之外的文件类型与步骤: 仅 xls/xlsx, 严格 6 步流程。

## 2. 三类导入的字段边界 (不重复)

关键约束: 同一字段只在一个入口导入, 避免职责混乱与口径不一致。

### 2.1 学生导入 (Student)

- 仅包含: 学生唯一标识 (学号/工号等)、姓名、性别、年级、学院/专业/班级等组织学籍属性、联系方式等学生自身属性。
- 明确不包含: 楼栋、房间号、床位号、宿舍 ID、入住状态等任何住宿相关字段。
- 学生管理页不再导入任何宿舍相关字段。

### 2.2 宿舍导入 (Dorm)

- 仅包含: 楼栋、房间号、楼层、容量、宿舍性别、宿舍年级等宿舍静态属性 (以现有字段字典为准)。
- 不包含: 学生入住信息、床位分配信息。

### 2.3 入住导入 (Check-in / Residency)

- 仅包含: 建立分配关系所需字段 (如学生唯一标识 + 宿舍定位字段 + 床位号, 以现有入住接口为准)。
- 不包含: 学生基础信息、宿舍静态属性。

## 3. 导入向导交互与步骤设计 (6 步)

交互参考 Navicat: 标准步骤式向导, 左侧 Steps + 右侧内容区 + 底部操作按钮, 每步校验通过才可进入下一步。

### Step 1: 下载模板 + 选择文件类型 (仅 xls/xlsx)

目的: 统一模板入口与格式约束, 降低列名不对或格式不对导致的导入失败。

页面内容

- 模板区: 下载模板 (按当前页面导入类型: 学生/宿舍/入住)。
- 文件类型选择: 仅展示 Excel (_.xls, _.xlsx), 其他类型不提供。

校验

- 未选择 Excel 类型或未完成模板确认不阻塞, 但进入下一步前必须上传符合格式的文件 (格式拦截在 Step 2)。

### Step 2: 上传文件 (Excel 需选择 workbook 和 sheet)

目的: 确保解析源明确, 可复现。

页面内容

- 上传区域: 选择文件 (xls/xlsx)。
- 上传成功后:
  - 选择 workbook (若 workbook=该文件, 可只读展示)。
  - 选择 sheet (下拉必选)。
  - 基础信息展示: 行数/列数 (能拿到则展示, 拿不到不强求)。

校验

- 文件格式校验: 非 xls/xlsx 阻断并提示。
- 未选择 sheet 阻断进入 Step 3。

### Step 3: 基础解析与字段对应 (双列表格映射 + 匹配状态)

目的: 将 Excel 表头与数据库字段显式对齐, 避免隐式写入错误。

页面结构

- 表头匹配状态概览: 已匹配列数 / 未匹配列数 / 多余列数。
- 字段映射表 (三列):
  - Source Field: 导入表标题列。
  - Target Field: 数据库字段列 (下拉选择)。
  - 字段说明: 含义 / 是否必填 / 值域提示。

规则

- 必填数据库字段必须完成映射, 否则禁止进入 Step 4。
- Excel 中多余未映射列默认忽略, 不阻断。

### Step 4: 数据预检 (a/b/c 三类检查)

目的: 导入前暴露风险, 支持问题行筛选与下载。

检查内容 (严格按 a/b/c)

a. 缺少必填项 (必填字段为空/缺列)

b. 部分字段值在已设置项中不存在 (枚举值/字典值不合法)

c. 部分字段值与数据库中已有内容冲突 (主键/唯一约束/业务冲突)

呈现方式

- 统计: 总行数、通过、问题行数 (可按错误/冲突/其他分类展示)。
- 明细表: 逐行展示问题原因 (错误码/原因/建议修复方式), 支持筛选“仅看问题行”。

导出

- 下载问题行文件 (原始数据 + 原因列/错误码列), 供线下修复后重导。

### Step 5: 冲突处理与导入策略 (覆盖 / 跳过)

目的: 明确冲突处理方式, 并提供可执行的重导闭环。

冲突处理方式

- 不在页面内逐条更正 (本期不建设)。
- 不符合要求的数据在 Step 4/5 可筛选并下载问题行文件, 修复后增量导入。

导入策略 (已确认)

- 覆盖已有数据
- 跳过重复数据

规则

- 用户必须选择其一 (默认策略由产品决定, 不新增第三种)。

### Step 6: 执行导入与结果复盘

目的: 执行过程可感知, 结果可复盘, 失败可重跑。

执行中

- 展示进度条与当前状态 (执行中/完成/失败)。

完成后结果卡片

- 成功 / 失败 / 跳过 数量。

下载

- 失败行文件
- 错误报告 (含错误码/原因/建议修复方式)

快捷操作

- 继续导入该页面的其他数据 (回到 Step 1 或关闭后保持当前页上下文)。

## 4. 页面接入与复用方式 (实施落地)

### 4.1 接入页面

- 学生管理页: 入口“导入”打开 Import Wizard (学生模式)。
- 宿舍管理页: 入口“导入”打开 Import Wizard (宿舍模式)。
- 入住管理页: 入口“导入”打开 Import Wizard (入住模式)。

### 4.2 配置驱动 (保证字段不重复、规则一致)

为三类导入分别提供一份配置 (仅用于向导渲染与校验):

- 模板定义: 模板列、必填列。
- 字段说明: 用于 Step 3 的字段说明列。
- 值域/已设置项来源: 用于 Step 4 的 b 类校验。
- 冲突判定依据: 用于 Step 4 的 c 类校验。
- 支持的导入策略: 覆盖/跳过。

## 5. 验收标准

- 学生管理页导入模板与字段映射中不存在楼栋/房间/床位等宿舍字段; 导入后学生记录也不会写入这些字段。
- 宿舍/入住导入字段与学生导入字段无重复; 各自模板与映射表中只出现其职责范围字段。
- 导入仅支持 xls/xlsx; 非 Excel 文件无法进入 Step 3。
- Excel 导入必须选择 sheet; 未选无法进入字段映射。
- Step 3 映射表为“导入表头 -> 数据库字段”的双列映射, 且包含字段说明列; 必填字段未映射不能进入 Step 4。
- Step 4 预检覆盖 a/b/c, 支持筛选问题行并下载问题行文件。
- Step 5 可选择“覆盖/跳过”; 并可通过问题行下载实现“修复后增量重导”。
- Step 6 有进度条; 完成后展示成功/失败/跳过数量, 并可下载失败行文件与错误报告。

6. 分阶段工程实施计划 (Engineering Implementation Plan) — 第二版
   总体策略

先构建通用 Import Wizard 组件骨架，以“宿舍管理页”作为试点场景打通闭环（模板 → 上传/选 Sheet → 映射 → 预检 → 策略 → 执行/复盘）。

宿舍试点稳定后，再以配置驱动方式复制到学生与入住导入（其中学生导入严格去除所有宿舍/入住字段）。

阶段 0：口径定版与试点准备 (Definition & Readiness)

目标：在进入开发前，把“字段边界、模板、字典项、错误码/预检规则”一次性对齐，避免后续返工。

0.1 交付物

DormImportDTO 字段清单定版（仅宿舍静态属性，无学生/入住字段）。

宿舍导入 Excel 模板（列名与 DTO 一一对应；标注必填/可选）。

宿舍字段字典（用于 Step3 字段说明列；用于 Step4 b 类校验的“已设置项范围”）。

预检规则与错误码清单（严格覆盖 a/b/c：必填缺失、字典值不存在、与库中冲突）。

问题行文件格式定义（导出列 + errorCode/reason/suggestion 三列规范）。

0.2 阶段验收门槛（Gate）

宿舍导入模板中不出现任何学生/入住相关列。

a/b/c 校验规则与错误码“能解释、可执行修复”。

阶段 1：核心组件构建 + 宿舍试点 MVP (Wizard Skeleton + Dorm Pilot)

目标：实现通用向导的“Step1–Step3 + 最小可用执行链路”，让宿舍导入先跑通“无冲突数据可入库”。

1.1 后端：解析与最小入库接口

(1) DTO 定义

定义 DormImportDTO：仅包含你 Gemini 版中列出的宿舍静态字段范围（楼栋、楼层、房间号、床位数/容量、性别限制、年级限制），并明确必填项（至少楼栋、房间号等以你们业务为准）。

明确：后端导入接口仅接收 DTO 对应字段，拒绝/忽略任何非 DTO 字段，确保数据边界不会被破坏。

(2) Excel 基础解析服务（供 Step2/Step3 使用）

入参：File + sheetName

出参：headers + previewRows(前 N 行) + totalRowCount(可选)

说明：该接口只负责“可被映射的结构化解析”，不承担预检逻辑（预检在阶段 2 增强）。

(3) 最小执行接口（无冲突场景）

入参：mappedFieldMap + parsedRows + strategy(可先不开放)

MVP 仅要求：当数据无冲突、必填齐全时，能成功写入宿舍表。

注：阶段 1 不要求完整预检 a/b/c 与策略执行；目的是先把向导骨架跑通，减少并行复杂度。

1.2 前端：向导骨架与 Step1–Step3

(1) Wizard 容器

Modal 结构：左侧 Steps + 右侧内容区 + 底部操作条（上一步/下一步/取消）。

通用流程控制：每一步具备“进入下一步前置校验”，不通过则阻断（按钮置灰或提示）。

(2) Step1：模板下载 + 文件类型

模板下载按钮指向“宿舍模板”。

文件类型仅显示/允许 xls/xlsx。

(3) Step2：上传 + Workbook/Sheet 选择

上传限制：仅 xls/xlsx。

选择 sheet 为必选；未选不得进入 Step3。

(4) Step3：字段映射（双列表格 + 说明列）

左列：Excel 表头

右列：DB/DTO 字段（下拉）

说明列：字段含义、是否必填、值域提示（来自阶段 0 字段字典）。

必填字段未映射：阻断进入下一步。

1.3 宿舍管理页集成（试点挂载）

在宿舍管理页导入入口挂载 Import Wizard（宿舍模式）。

注入宿舍专属配置：模板地址、字段字典、必填字段列表。

1.4 阶段验收门槛（Gate）

用户可完成 Step1–Step3，且能把“无冲突、必填齐全”的宿舍 Excel 成功导入。

Step3 必填未映射时 Next 必须阻断。

阶段 2：预检能力完整化 + 冲突策略闭环 (Precheck & Strategy)

目标：把你已确认的 Step4/Step5/Step6 做到可用且可复盘：a/b/c 预检、覆盖/跳过策略、失败行与错误报告下载。

2.1 后端：预检接口（严格 a/b/c）

预检输出必须结构化，以支撑前端筛选与导出：

输入：DormImportDTO[]（由解析+映射后的行）

输出：

totalCount / passCount / issueCount

issues[]：每条包含 rowNo、type(a|b|c)、field、errorCode、message、suggestion

校验范围

a 必填缺失：非空校验（缺列/空值）

b 字典值不存在：例如楼栋/性别/年级等（以阶段 0 字典为准）

c 与库中冲突：宿舍主键冲突（例如 楼栋+房间号 已存在；以你们既有唯一约束为准）

2.2 前端：Step4 预检页与问题可视化/下载

统计卡片：总行/通过/问题（并能按 a/b/c 分组显示）

问题行明细表：

支持筛选“仅看问题行”

行级展示错误码、原因、建议修复方式

问题行下载：

下载“问题行文件”（原始数据 + 错误信息列）

下载“错误报告”（错误码/原因/建议修复方式汇总）

2.3 Step5：冲突策略（仅覆盖/跳过）与参数透传

前端仅提供两项策略：

覆盖已有数据

跳过重复数据

后端执行接口接收 strategy 并按策略写库，返回：

成功/失败/跳过数量

失败行列表（含 errorCode/reason/suggestion），用于前端生成失败行文件

2.4 Step6：执行与结果复盘

前端展示进度条（阶段式即可：执行中/完成）。

完成后结果卡片固定输出：

成功 / 失败 / 跳过数量

下载：失败行文件、错误报告

快捷操作：继续导入（回到 Step1，仍在宿舍管理上下文）

2.5 阶段验收门槛（Gate）

能稳定复现并通过验收用例：

Step4：必填缺失（a）能定位到行并给出修复建议

Step4：字典值非法（b）能定位到行并给出修复建议

Step5：制造冲突数据（c）

选“跳过”则结果页显示跳过数量且库不变

选“覆盖”则库内记录被更新且结果页体现覆盖效果

能下载“问题行文件/失败行文件/错误报告”。

阶段 3：组件配置化抽象 + 推广到学生与入住 (Config-driven Rollout)

目标：宿舍试点验证后，将 Import Wizard 抽象为“配置驱动”，在不复制业务代码的情况下接入学生与入住导入。

3.1 组件抽象化（去宿舍硬编码）

将与“宿舍字段、宿舍字典、宿舍冲突规则”相关的内容全部外置到 Config：

template（模板下载）

fields（字段清单、必填、说明）

dictionaries（用于 b 类校验）

uniqueKeys（用于 c 类校验）

strategies（覆盖/跳过）

Wizard 核心仅负责：流程状态机 + 通用 UI 渲染 + 调用解析/预检/执行接口。

3.2 学生管理页接入（严格遵循你的决策）

定义 Student Config：

只包含学生自身属性字段

不包含楼栋/房间/床位号/宿舍 ID 等任何宿舍与入住冗余字段

重点验证：b 类“已设置项”校验（如学院/专业/班级/年级等）与 c 类主键冲突（如学号已存在）

3.3 入住管理页接入

定义 Check-in Config：仅包含建立关联关系所需字段（按现有入住导入接口要求配置）。

重点验证：c 类业务冲突（如关联对象不存在/重复分配等，具体以你们现有接口返回为准）。

3.4 阶段验收门槛（Gate）

三页面（宿舍/学生/入住）均使用同一 Import Wizard 组件。

字段不重复原则被严格执行：学生模板与映射中不出现宿舍/入住字段。

步骤 功能点 验收标准
